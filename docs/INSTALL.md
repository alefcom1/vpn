# Пошаговая установка

От пустого аккаунта Hetzner до работающего VPN в Happ. Значения подставлены реальные:
домен `traduzione.tech`, сервер `178.105.192.76`.

Порядок важен: DNS должен быть настроен **до** запуска `bootstrap.sh`, иначе Let's Encrypt
не выдаст сертификаты.

---

## Шаг 0. Что понадобится

- аккаунт Hetzner Cloud;
- домен `traduzione.tech` с возможностью менять NS или DNS-записи;
- аккаунт Cloudflare (бесплатный);
- SSH-ключ;
- телефон с приложением-аутентификатором (для 2FA панели).

---

## Шаг 1. SSH-ключ

На своём компьютере (не на сервере):

```bash
ssh-keygen -t ed25519 -C "vpn-hetzner" -f ~/.ssh/vpn_hetzner
cat ~/.ssh/vpn_hetzner.pub
```

Публичный ключ понадобится на следующем шаге. Приватный (`~/.ssh/vpn_hetzner`) никуда
не копировать.

Узнать свой внешний IP — пригодится для ограничения SSH:

```bash
curl -s https://api.ipify.org
```

Если у провайдера динамический IP, ограничение по IP лучше не включать.

## Шаг 2. Сервер в Hetzner

Hetzner Cloud → **Add Server**:

| Параметр | Значение |
|---|---|
| Location | **Helsinki (fi-hel1)** |
| Image | **Debian 13** (или 12) |
| Type | **Shared vCPU → x86 → CX22** |
| Networking | IPv4 + IPv6 |
| SSH keys | добавить публичный ключ из шага 1 |
| Firewalls | не подключать — firewall настроит `bootstrap.sh` |
| Backups | по желанию (+20 % к цене) |

> **Почему x86, а не ARM (CAX11):** панель разворачивается в docker
> (backend + PostgreSQL + Valkey), и на x86 нет риска упереться в отсутствие
> arm64-образов. Цена та же.

После создания проверить вход:

```bash
ssh -i ~/.ssh/vpn_hetzner root@178.105.192.76
```

Если сервер получил другой IP — использовать его и поправить `.env` на шаге 5.

## Шаг 3. DNS в Cloudflare

1. Cloudflare → **Add a site** → `traduzione.tech` → план **Free**.
2. Cloudflare покажет два NS-сервера. Прописать их у регистратора домена
   вместо текущих. Делегирование занимает от 10 минут до нескольких часов.
3. Когда домен станет `Active`, создать записи в **DNS → Records**:

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `panel` | `178.105.192.76` | **DNS only** (серое облако) |
| A | `hy2` | `178.105.192.76` | **DNS only** (серое облако) |

Проксирование панели включим **после** выпуска сертификата (шаг 16).
Для `hy2` проксирование не включаем **никогда**: Cloudflare не проксирует UDP,
а Hysteria2 работает по UDP.

4. **SSL/TLS → Overview** → режим **Full (strict)**.

Проверить, что записи разъехались — **обязательно с явным резолвером**:

```bash
dig +short panel.traduzione.tech @1.1.1.1
dig +short hy2.traduzione.tech @1.1.1.1
```

Обе команды должны вернуть `178.105.192.76`. Не идти дальше, пока это не так.

> **Если `dig` отвечает `connection timed out; no servers could be reached`** — это не про
> домен, а про то, что `dig` не достучался до резолвера. На macOS `dig` читает
> `/etc/resolv.conf` напрямую, а система резолвит через mDNSResponder со своей
> конфигурацией: браузер работает, `dig` — нет. Обычные причины: активный VPN-клиент
> перехватил DNS, провайдер режет исходящий порт 53, или `/etc/resolv.conf` пуст после
> отключения предыдущего VPN. Обходные проверки:
>
> ```bash
> dscacheutil -q host -a name panel.traduzione.tech   # системный резолвер macOS
> nslookup panel.traduzione.tech 1.1.1.1
> cat /etc/resolv.conf && scutil --dns | head -40     # если нужна причина
> ```
>
> Ответ `NXDOMAIN` или пустой вывод — вот это действительно «записи ещё не разъехались».

## Шаг 4. Установка репозитория на сервер

Сначала **только подключение**:

```bash
ssh -i ~/.ssh/vpn_hetzner root@178.105.192.76
```

Убедиться, что приглашение сменилось на `root@<hostname>`. Если вставить весь блок
разом и SSH не подключится, остальные команды тихо выполнятся на локальной машине.

Затем, уже на сервере:

```bash
apt update && apt install -y git
git clone https://github.com/alefcom1/vpn.git /root/vpn
cd /root/vpn
```

> **`Permission denied (publickey)`** означает, что сервер жив и SSH работает, но твоего
> ключа у него нет. Ключ привязывается к серверу в момент создания. Варианты: подключиться
> с той машины, где ключ лежит; пересоздать сервер с нужным ключом (он ещё пустой);
> или добавить ключ через Hetzner Cloud → Console (пароль root при необходимости
> сбрасывается там же, вкладка Rescue):
>
> ```bash
> mkdir -p /root/.ssh && chmod 700 /root/.ssh
> echo 'ssh-ed25519 AAAA... vpn-hetzner' >> /root/.ssh/authorized_keys
> chmod 600 /root/.ssh/authorized_keys
> ```

## Шаг 6. Установка

```bash
./bootstrap.sh
```

Скрипт займёт 3–7 минут и сделает: обновление системы, BBR, лимиты, харденинг SSH,
docker, firewall, панель за Caddy с сертификатами, каталог ноды, geo-списки, cron.

**Скрипт завершился с предупреждением про сертификат** — значит Caddy его ещё не выписал.
Смотреть причину:

```bash
docker logs caddy --tail 50
```

Частые причины: A-запись не разъехалась, включено проксирование Cloudflare,
порт 80 занят. После исправления:

```bash
HY2_DOMAIN=hy2.traduzione.tech /opt/vpn/sync-certs.sh
```

Проверка, что всё поднялось:

```bash
docker ps                      # remnawave, remnawave-db, remnawave-redis, caddy
ss -lntp | grep -E ':(80|8443)'
```

## Шаг 7. Подбор сайта-донора для REALITY

REALITY заимствует TLS-хендшейк реального чужого сайта. От качества выбора зависит,
насколько канал незаметен.

Требования:

- TLS 1.3 и ALPN `h2`;
- сервер физически в стране VPS (Финляндия/Германия), не за глобальным CDN;
- отдаёт контент без редиректа на другой домен;
- не заблокирован в РФ;
- не «затаскан» публичными VPN-сервисами.

Проверка кандидата:

```bash
openssl s_client -connect www.candidate.com:443 -tls1_3 -alpn h2 \
  -servername www.candidate.com </dev/null 2>&1 \
  | grep -E 'Protocol|Cipher|ALPN|Verify return'
```

Годится, если видно `TLSv1.3`, `ALPN protocol: h2`, `Verify return code: 0`.

Записать выбранный домен в `.env`:

```bash
nano /root/vpn/.env      # REALITY_DEST=www.candidate.com
```

## Шаг 8. Генерация конфига Xray

```bash
cd /root/vpn
./scripts/render-xray-template.sh
```

Скрипт сгенерирует ключи REALITY (один раз, дальше берёт из `.env`), подставит домены
и порты и запишет готовый конфиг в `/opt/vpn/xray-config.json`. В конце выведет
значения, которые понадобятся в панели — **сохранить их**:

```
REALITY public key : ...
REALITY short id   : ...
REALITY SNI / dest : ...
gRPC serviceName   : ...
Hysteria2 SNI      : hy2.traduzione.tech
```

Хочешь блокировать РФ-направление на сервере (см. RUNBOOK §3) — запускать с
`--ru-guard`. Решить это лучше сразу: смена конфига позже потребует перезапуска ноды.

Показать конфиг для копирования:

```bash
cat /opt/vpn/xray-config.json
```

## Шаг 9. Первый вход в панель

Открыть `https://panel.traduzione.tech:8443`.

1. Создать администратора — пароль длинный, сохранить в менеджер паролей.
2. **Сразу включить 2FA** в настройках профиля. Панель управляет доступом всех

## Шаг 10. Создание ноды

Панель → раздел **Nodes** → создать ноду:

| Поле | Значение |
|---|---|
| Name | `main` |
| Address | `172.17.0.1` |
| Port | `2222` |

Адрес именно `172.17.0.1` — это адрес хоста со стороны docker. Панель работает
в контейнере, а нода слушает на хосте.

Панель выдаст ключ (сертификат ноды). Скопировать его целиком и на сервере:

```bash
nano /opt/remnanode/.env      # заменить строку SSL_CERT=PASTE_FROM_PANEL
cd /opt/remnanode && docker compose up -d
docker logs remnanode --tail 30
```

Через 10–20 секунд нода в панели должна стать зелёной.

## Шаг 11. Конфиг Xray в панель

Панель → раздел конфигурации ядра (**Xray Config** / шаблон конфига) → вставить
целиком содержимое `/opt/vpn/xray-config.json` → сохранить.

Нода перезапустится сама. Проверить, что порты поднялись:

```bash
ss -lntp | grep -E ':(443|2087)'    # TCP: REALITY и gRPC
ss -lnup | grep ':443'              # UDP: Hysteria2
docker logs remnanode --tail 50     # ошибок быть не должно
```

Если Xray не стартовал — почти всегда опечатка в `REALITY_DEST` или отсутствующий
сертификат для Hysteria2 (`ls -l /opt/remnanode/ssl/`).

## Шаг 12. Хосты (то, что увидит клиент)

Для каждого inbound'а из конфига создать в панели хост. Значения — из вывода шага 8.

**1. Основной — VLESS TCP REALITY Vision**

| Поле | Значение |
|---|---|
| Remark | `🇩🇪 Белые списки` |
| Address | `178.105.192.76` |
| Port | `443` |
| Inbound | `VLESS-TCP-REALITY` |
| SNI | `<REALITY dest>` |
| Public key | `<REALITY public key>` |
| Short ID | `<REALITY short id>` |
| Flow | `xtls-rprx-vision` |

> `Flow` обязателен: без него не будет сплайсинга, вырастет нагрузка на процессор
> и появится паттерн TLS-in-TLS, который и ловят. **Mux не включать** — он ломает Vision.

**2. Резерв — VLESS gRPC REALITY**

То же самое, но `Port 2087`, inbound `VLESS-GRPC-REALITY`, `serviceName` из шага 8,
`Flow` пустой (с gRPC Vision не работает). Remark: `🇩🇪 Резерв gRPC`.

**3. Резерв — Hysteria2**

| Поле | Значение |
|---|---|
| Remark | `🇩🇪 Резерв Hysteria2` |
| Address | `hy2.traduzione.tech` |
| Port | `443` |
| Inbound | `HYSTERIA2` |
| SNI | `hy2.traduzione.tech` |

Здесь адрес — **домен, а не IP**: клиент проверяет имя в сертификате.

## Шаг 13. Подписка и профили

Панель → **Templates**:

- **Xray-JSON** — формат, который получит Happ. Именно сюда попадают правила
  роутинга, поэтому профили «Белые списки» / «Обходы» / «Всё через VPN» различаются
  здесь.
- **Subscription page** — страница по ссылке подписки: кнопки установки клиентов
  и импорт в один клик.

Панель → настройки подписки → **HAPP Routing**: встроенный конструктор правил.
Собрать три набора и вставить ссылки в поле `happRouting`:

| Профиль | Правило |
|---|---|
| Белые списки | российские домены и IP → напрямую, остальное → через VPN |
| Обходы | заблокированное → через VPN, остальное → напрямую |
| Всё через VPN | без исключений |

Начать проще с «Белых списков» — он закрывает 90 % задач.

## Шаг 14. Первый пользователь

Панель → **Users** → создать:

| Поле | Значение |
|---|---|
| Username | `alef-phone` |
| Traffic limit | без лимита (для себя) |
| Expire | без срока |
| Hosts | все три |

Скопировать ссылку-подписку. Она вида:

```
https://panel.traduzione.tech:8443/api/sub/<short-uuid>
```

**Раздавать всегда подписку, а не голый `vless://`.** При смене сервера, портов или
ключей конфиг обновится у всех сам — иначе придётся переписываться с каждым.

Отдельный пользователь на каждое устройство и каждого человека: иначе статистика
бессмысленна, а отзыв доступа невозможен без отключения остальных.

## Шаг 16. Проверка

На сервере:

```bash
ss -lntp | grep -E ':(443|2087|8443)'
ss -lnup | grep ':443'
curl -Ik https://178.105.192.76 | head -3     # должен ответить сайт-донор
sysctl -n net.ipv4.tcp_congestion_control     # bbr
docker stats --no-stream
```

С устройства при включённом VPN:

- заблокированный ресурс открывается;
- `2ip.ru` показывает IP сервера;
- российский сайт видит домашний IP;
- Госуслуги и банк-клиент открываются;
- нет утечек DNS, WebRTC, IPv6;
- переключение Wi-Fi ↔ LTE не рвёт сессию;
- **проверить на мобильном операторе отдельно** — там DPI агрессивнее, и именно
  там понадобятся резервные профили.

Переключиться на `🇩🇪 Резерв Hysteria2` и `🇩🇪 Резерв gRPC`, убедиться, что оба работают.

## Шаг 17. Закрыть панель за Cloudflare

Сертификаты выписаны, можно включать проксирование.

1. Cloudflare → DNS → запись `panel` → **Proxied** (оранжевое облако).
2. Запись `hy2` **оставить серой**.
3. Проверить, что панель открывается: `https://panel.traduzione.tech:8443`.

Теперь реальный IP сервера не виден в DNS для панели. Дополнительно можно ограничить
доступ к панели по стране или списку IP в **Security → WAF**.

Продление сертификатов: Caddy пойдёт по HTTP-01 на порт 80 через Cloudflare —
это работает при `Full (strict)`. Если продление начнёт падать, временно выключить
проксирование, дождаться выпуска, включить обратно.

## Шаг 18. Раздача знакомым

1. Панель → Users → создать пользователя: имя, **лимит трафика**, **срок действия**.
2. Отправить ссылку-подписку или QR-код из панели.
3. Человек ставит Happ, открывает ссылку, выбирает `Белые списки`, жмёт кнопку.
4. Отзыв доступа — выключить пользователя в панели.

Настройки со стороны знакомого не требуются: правила роутинга приезжают в подписке.
