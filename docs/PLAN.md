# План разработки личного VPN на Hetzner

Цель: свой VPN на 1 сервере Hetzner, лёгкий по CPU/RAM, с раздельным трафиком
(российские ресурсы — напрямую, заблокированные — через тоннель) и включением в один тумблер.

---

## 0. Итоговое решение (TL;DR)

| Параметр | Выбор |
|---|---|
| Ядро | **Xray-core** (сервер), **sing-box** (клиент) |
| Основной протокол | **VLESS + XTLS-Vision + REALITY**, TCP/443 |
| Резервные каналы | **Hysteria2** на UDP/443 (в том же Xray-core) + VLESS/gRPC на 2087 |
| Сервер | Hetzner **CX22** (x86, 2 vCPU / 4 GB / 20 TB), Helsinki |
| Раздельный трафик | **на клиенте** (rule-set), сервер — только guard-rails |
| Клиент | **Happ** (iOS/macOS/Android/Windows/TV) — тумблер, профили, счётчик трафика |
| Панель | **Remnawave** — HAPP Routing Builder, страница подписки, статистика |
| Формат подписки | **JSON** (не base64) — иначе не передать правила роутинга |
| Ожидаемая нагрузка | Xray 25–60 МБ, панель +0.6–1 ГБ из 4 ГБ. CPU ~5–15 % на 300 Мбит |
| Стоимость | ~4 €/мес + домен |
| Reverse proxy | Caddy (авто-TLS Let's Encrypt), панель на порту 8443 |

## 1. Выбор протокола — обоснование

| Протокол | DPI-устойчивость (РФ, 2026) | CPU | RAM | Вердикт |
|---|---|---|---|---|
| **VLESS + REALITY + XTLS-Vision** | Высокая: TLS-handshake заимствуется у реального чужого сайта, активное зондирование отдаёт настоящий сайт. Vision убирает паттерн TLS-in-TLS | Минимальный (splice, без двойного шифрования) | ~25–60 МБ | **Основной** |
| VLESS + REALITY + gRPC / httpupgrade | Высокая, лучше проходит кривые NAT и корп-прокси, но есть двойное шифрование (нет splice) | +20–40 % к Vision (HTTP/2-фрейминг) | +10–20 МБ | Резервный inbound на том же сервере |
| VLESS + XHTTP + TLS (можно через CDN) | Средняя-высокая, современная замена WS/gRPC для CDN-сценария | Средний | Средний | Резервный inbound |
| VLESS + WS + TLS + CDN (Cloudflare) | Средняя (TLS-in-TLS палится), зато переживает бан IP сервера | Высокий | Средний | Аварийный, нужен домен |
| Hysteria2 (QUIC/UDP) | Средняя: UDP в РФ местами режут, но когда оператор душит именно TCP — работает | Высокий (userspace UDP) | Средний | **Включён как резерв.** Реализован внутри Xray-core, отдельный демон не нужен |
| AmneziaWG | Средняя-высокая, обфусцированный WireGuard | **Минимальный (ядро)** | ~5 МБ | Аварийный канал, простой и дешёвый |
| Shadowsocks-2022 / ShadowTLS v3 | Средняя (энтропийный детект AEAD) | Низкий | Низкий | Не нужен при наличии REALITY |
| OpenVPN / IKEv2 / L2TP / голый WireGuard | Низкая, детектируются сигнатурно | — | — | Не использовать как основной |

**Вывод:** `VLESS + REALITY + XTLS-Vision` на 443/TCP — лучший на сегодня баланс
«незаметность / скорость / потребление ресурсов». Второй inbound gRPC и UDP-канал —
страховка, включаются одной строкой в конфиге.

Важно: с Vision **не включать mux** — он ломает splice и добавляет CPU.

## 2. Инфраструктура (Hetzner)

- **Тариф:** CAX11 (ARM64, 2 vCPU, 4 GB, 40 GB NVMe, 20 ТБ трафика) — дешевле и
  производительнее CX22 на ту же цену. Xray/sing-box имеют официальные arm64-сборки.
- **Локация:** Helsinki (fi-hel1) — минимальный RTT до СПб (~10–15 мс) и Москвы (~25–35 мс).
  Nuremberg/Falkenstein — +15–20 мс, но больше «шума» из соседних сервисов.
- **IPv6:** бесплатный /64 — включить, полезно для доступа к части ресурсов.
- **Cloud Firewall (бесплатный):** входящие только `443/tcp`, `443/udp`, `<порт резерва>/udp`,
  `22/tcp` — с allowlist по своему IP или полностью закрыт (доступ через Hetzner Console).
- **Снапшот** после настройки — для восстановления/клона за 5 минут.
- **Риски:** подсети Hetzner известны и частично фильтруются как РФ-сервисами, так и РКН.
  Держать наготове скрипт разворачивания (см. §10) и запасную локацию.
- **ToS:** только личное использование, без публичного сервиса и abuse-нагрузки.

## 3. Базовая настройка ОС

1. Debian 13 minimal (или 12), `apt full-upgrade`, `unattended-upgrades`.
2. SSH: только ключи, `PasswordAuthentication no`, `PermitRootLogin prohibit-password`,
   отдельный непривилегированный пользователь.
3. Сеть (`/etc/sysctl.d/99-vpn.conf`):
   - `net.core.default_qdisc=fq`, `net.ipv4.tcp_congestion_control=bbr`
   - `net.core.rmem_max=16777216`, `net.core.wmem_max=16777216`
   - `net.ipv4.tcp_fastopen=3`, `net.core.somaxconn=8192`
   - `net.ipv4.ip_forward=1` (нужно только для WG-канала)
4. `ulimit -n 65535` (LimitNOFILE в systemd-юните).
5. Синхронизация времени: `chrony`.
6. Удалить лишнее (snapd, exim, ненужные таймеры) — экономия 30–80 МБ RAM.

## 4. Сервер: Xray + REALITY

1. Установка бинаря из официального релиза (не docker — экономия RAM), systemd-юнит
   с харденингом: `NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`,
   `AmbientCapabilities=CAP_NET_BIND_SERVICE`, `User=xray`, `MemoryMax=256M`.
2. Сгенерировать: `UUID` (по одному на каждое устройство), `x25519` keypair, 2–4 `shortId`.
3. **Подбор REALITY `dest`** — критерии:
   - TLS 1.3 + X25519 + ALPN `h2`;
   - сервер физически в стране VPS (Финляндия/Германия), не за глобальным CDN;
   - без редиректа на другой домен, отдаёт содержимое по IP;
   - не заблокирован в РФ и не «затаскан» как популярный dest;
   - проверка: `openssl s_client -connect <dest>:443 -tls1_3 -alpn h2 -servername <dest>`.
4. Конфиг сервера:
   - `log`: `loglevel: none`, `access: none` (RAM + приватность);
   - `policy`: `handshake: 4`, `connIdle: 300`, `bufferSize: 512` (или 0 для минимума RAM);
   - `sniffing`: `destOverride: [http, tls, quic]` — нужно для доменного роутинга;
   - `stats` выключить (если не нужен учёт трафика).
5. **Guard-rails в routing на сервере** (важно):
   - `block` для приватных сетей (`geoip:private`) — защита от SSRF в свою LAN;
   - `block` для `bittorrent` (протокол) — abuse-политика Hetzner;
   - `block` для `geosite:category-ru` + `geoip:ru` — «канарейка»: если клиент по ошибке
     отправит РФ-трафик в тоннель, он не пойдёт с немецкого IP молча, а сразу отвалится
     и ошибка станет видна. Это и защита от бана аккаунтов в РФ-сервисах.
   - опционально `geosite:category-ads-all` → block.
6. Второй inbound (VLESS+REALITY+gRPC) на том же 443 через разный SNI/dest либо на 8443 —
   как резерв для сетей, где Vision не проходит.

## 5. Раздельный трафик (главная часть)

Разделение делается **на клиенте**. На сервере оно бессмысленно: сервер в ЕС,
и РФ-сайт всё равно увидит немецкий IP.

### Два режима

**Режим A — «Белый список РФ» (по умолчанию, рекомендуемый)**
`РФ-домены и РФ-IP → direct, всё остальное → proxy`.
Плюсы: ничего не ломается, банки/госуслуги/маркетплейсы работают с домашнего IP,
не нужно поддерживать список блокировок. Минус: больше трафика через VPS.

**Режим B — «Только заблокированное»**
`Список заблокированных → proxy, всё остальное → direct`.
Плюсы: минимум трафика и задержек. Минусы: список надо регулярно обновлять,
часть сервисов геоблокирует по IP и в списки РКН не входит (не откроется без правки).

Реализовать оба как отдельные профили подписки и переключать в клиенте.

### Порядок правил (sing-box)

1. `private` / LAN / loopback → **direct**
2. DNS-роутинг (см. §6)
3. `rule_set: geoip-ru`, `geosite-category-ru` → **direct**
4. Явные исключения-direct по доменам и (на Android) по package name:
   банк-клиенты, Госуслуги, налоговая, маркетплейсы, Яндекс, VK, Mail.ru, Сбер, МТС/Билайн.
5. Режим B: `rule_set: re-filter-domains` + `re-filter-ipsum` → **proxy**, иначе direct.
6. Режим A: всё оставшееся → **proxy**.
7. Опционально `geosite-category-ads-all` → **block**.

### Источники списков

- `SagerNet/sing-geoip`, `SagerNet/sing-geosite` — SRS rule-set для sing-box.
- `Loyalsoldier/v2ray-rules-dat` — `geosite:category-ru`, `geoip:ru` для Xray-клиентов.
- `1andrevich/Re-filter-lists` — именно заблокированные в РФ домены и IP (есть сборки `.srs`/`.dat`) — основа режима B.
- `antifilter.download` — ipsum/community-подсети, дополнение к режиму B.

Автообновление: cron на сервере раз в сутки тянет списки, пересобирает rule-set и
подписку; клиенты подтягивают подписку по URL автоматически.

### Известные подводные камни

- Telegram, Steam, часть Google — CDN-узлы в РФ: попадают в `geoip:ru` и уйдут в direct,
  хотя нужны через прокси. Решение: доменные правила выше IP-правил + явный список исключений.
- «Белый список» не покрывает РФ-сервисы на зарубежных CDN — добавлять точечно по мере обнаружения.
- Не отправлять в тоннель локальные сети/принтеры/умный дом.

## 6. DNS

- **Клиент, split-DNS:**
  - домены из RU-набора резолвятся напрямую (Яндекс DNS `77.88.8.8` / DNS провайдера) —
    иначе получишь «не тот» CDN-узел и деградацию скорости;
  - остальные — DoH/DoT (Cloudflare/Google) **через тоннель** — защита от подмены ТСПУ;
  - `fakeip` — опционально, ускоряет, но ломает часть приложений: включать после тестов.
- **Сервер:** блок `dns` в Xray → `1.1.1.1`, `8.8.8.8`, `queryStrategy: UseIP`, кэш включён.
- Обязательная проверка на DNS-leak и на отсутствие резолва РФ-доменов через тоннель.

## 7. Клиент (Happ), панель управления и раздача доступов

### 7.1 Важное уточнение

**Happ — это клиент, а не панель.** Экран с большой кнопкой включения, таймером,
пингом, счётчиком трафика и списком профилей («Белые списки», «Обходы») — это
приложение на устройстве. Отдельно писать его не надо: Happ ставится из стора
(iOS / macOS / Android / Windows / Android TV) и бесплатен.

Поэтому задача делится на две части:

- **Клиент** = Happ. Наша работа — отдать ему такую подписку, чтобы экран выглядел
  ровно как на скриншоте: несколько именованных профилей с флагами, счётчик трафика,
  срок действия, метки протоколов.
- **Панель** = админка на сервере: пользователи, статистика, ссылки, QR, вкл/выкл.

### 7.2 Что нужно от сервера, чтобы Happ выглядел как на скриншоте

| Элемент интерфейса Happ | Что отдаёт сервер |
|---|---|
| Список профилей с названиями и флагами | Подписка с несколькими записями; имя профиля = поле `remarks` / имя записи |
| Метки `VLESS \| TCP \| Reality \| JSON` | Тип inbound'а и формат подписки |
| `321.91 GiB / 603.00 GiB` | HTTP-заголовок `Subscription-Userinfo: upload=…; download=…; total=…; expire=…` |
| Срок действия | тот же заголовок, поле `expire` |
| Разное поведение профилей («Белые списки» / «Обходы») | **JSON-подписка** (не base64): в конфиге едут правила роутинга |
| Импорт в один тап | deeplink `happ://` со ссылкой на подписку |

Ключевой вывод: подписка должна быть **JSON**, а не классическая base64-строка —
именно она позволяет положить внутрь правила split-tunneling и получить разные
профили с разным поведением, как на скриншоте.

### 7.3 Выбор панели

| Панель | RAM | Стек | Интеграция с Happ | Вердикт |
|---|---|---|---|---|
| **3x-ui** | 30–60 МБ | Go + SQLite, один бинарь | Базовая: подписка (в т.ч. JSON), `Subscription-Userinfo`, QR. Красивую страницу подписки и happ-роутинг — руками | Минимум ресурсов |
| **Remnawave** | 600 МБ–1 ГБ | Node + PostgreSQL + Redis, docker | Родная: страница подписки в стиле Happ, импорт по `happ://` в один клик, раздача наборов правил роутинга, мультипрофильные подписки, статистика по пользователям и нодам | Ближе всего к скриншоту |
| Marzban | 200–400 МБ | Python + SQLite/MySQL | Средняя: шаблоны подписки настраиваются | Компромисс |

**Важно про ресурсы:** вес панели — это control plane. На скорость и CPU под нагрузкой
он не влияет: трафик всё равно обрабатывает Xray (те же 25–60 МБ). Разница между
3x-ui и Remnawave — это ~0.5–1 ГБ постоянно занятой памяти из 4 ГБ, а не потеря скорости.

**Решение: Remnawave.** Подтверждено наличие HAPP Routing Builder (конструктор правил
роутинга для Happ прямо в дашборде, результат кладётся в поле `happRouting` настроек
подписки), шаблонов Xray-JSON / sing-box / Mihomo и конструктора страницы подписки —
то есть весь Happ-опыт закрывается штатными средствами панели.

**Влияние на выбор сервера:** панель разворачивается через docker (backend + PostgreSQL +
Valkey), поэтому берём **CX22 (x86_64)** вместо CAX11 (ARM) — исключаем риск отсутствия
arm64-образов. Цена та же.

**Состав стека на одном сервере:** Caddy (TLS, порт 8443) → Remnawave backend (127.0.0.1:3000)
→ Remnawave Node в host-режиме с Xray на 443 и 2087. Панель Xray-core в себе не содержит,
нода — обязательный отдельный компонент, но на этом же хосте.

### 7.4 Матрица профилей в подписке

Один сервер, один-два inbound'а — но в Happ это выглядит как список из 5 профилей:

| Профиль в Happ | Inbound | Роутинг внутри профиля |
|---|---|---|
| `🇩🇪 Белые списки` (основной) | VLESS / TCP / Reality / Vision | РФ-домены и IP → direct, остальное → тоннель |
| `🇩🇪 Обходы` | тот же | Список заблокированного → тоннель, остальное → direct |
| `🇩🇪 Всё через VPN` | тот же | Всё → тоннель |
| `🇩🇪 Резерв gRPC` | VLESS / gRPC / Reality | как «Белые списки» |
| `🇩🇪 Резерв Hysteria2` | Hysteria2, UDP 443 | как «Белые списки» |
| `🇩🇪 Резерв XHTTP` | VLESS / XHTTP / TLS (можно через CDN) | как «Белые списки» |

Первые три профиля — **один и тот же inbound с разными правилами в JSON-конфиге**,
дополнительных ресурсов сервера не потребляют. Резервные — второй и третий inbound
на других портах, на случай, когда основной транспорт не проходит у оператора.

### 7.5 Домен и безопасность панели

- Домен нужен для панели и подписки (~1–2 €/год). **На VPN он не влияет** — REALITY
  домена не требует. Заблокируют домен — тоннель продолжит работать.
- Cloudflare (free) с проксированием поддоменов панели и подписки: реальный IP не виден
  в DNS, TLS бесплатный, доступ ограничивается по стране/IP. Проксируемые порты: 8443, 2096.
- Панель: случайный путь (32 hex), сильный пароль, **2FA включить сразу**, TLS Let's Encrypt.
- Firewall наружу: `443/tcp` (VPN), `8443/tcp` (панель), `2096/tcp` (подписка),
  SSH — по allowlist. Всё остальное закрыто.
- Резервный доступ к панели — SSH-туннель на localhost, на случай блокировки домена.

### 7.6 Раздача доступов знакомым

1. В панели создать пользователя: метка, лимит трафика, срок действия, свой UUID.
2. Отдать **ссылку-подписку или `happ://`-deeplink** — не голый `vless://`.
   При смене сервера, порта или ключей конфиг обновится у всех сам.
3. Для телефона — QR-код из панели.
4. Знакомый ставит Happ, вставляет ссылку (или жмёт deeplink), выбирает профиль
   «Белые списки», жмёт кнопку. Настройка с его стороны — нулевая.
5. Отзыв доступа — отключение пользователя в панели, одна кнопка.
6. Уведомления об исчерпании трафика и истечении срока — Telegram-бот панели.

## 8. Тестирование (чек-лист приёмки)

- Скорость: `iperf3` и speedtest через тоннель — цель ≥ 300 Мбит на CAX11.
- Задержка и jitter; проверка YouTube 4K и видеозвонка.
- **Direct-путь:** РФ-сайт показывает домашний IP; открываются Госуслуги и банк-клиент.
- **Proxy-путь:** заблокированные ресурсы открываются, `2ip.ru` показывает IP сервера.
- Утечки: DNS-leak, WebRTC-leak, IPv6-leak.
- Активное зондирование: `curl -Ik https://<IP сервера>` и `openssl s_client` →
  должен вернуться сертификат и контент dest-сайта, а не «пустой» ответ.
- Ресурсы: `systemd-cgtop`, RSS процесса xray под нагрузкой 100/300 Мбит.
- Устойчивость: смена сети Wi-Fi ↔ LTE, реконнект, поведение при недоступности сервера.
- Мобильный интернет (Билайн/МТС/Мегафон) — там DPI агрессивнее, проверять отдельно.

## 9. Мониторинг и эксплуатация

- `vnstat` — контроль лимита 20 ТБ/мес.
- Cron-хелсчек (bash, ~0 ресурсов): порт жив / RSS в норме / место на диске / трафик —
  алерт в Telegram при отклонении.
- Логи выключены; при отладке включать временно.
- Еженедельно: обновление geo-файлов и списков, `apt upgrade`, проверка релиза Xray
  (версию пинить, обновлять осознанно).
- Безопасность: отдельный UUID на устройство, ротация `shortId`/UUID при подозрении на детект.
- DR: снапшот + скрипт разворачивания, смена IP за ~10 минут.

## 12. Риски и что делать

| Риск | Митигация |
|---|---|
| Бан IP сервера со стороны РКН | Снапшот + `bootstrap.sh`; смена IP/локации за 10 мин; запасной канал на другом порту |
| Блокировка подсети/AS Hetzner | Второй провайдер как холодный резерв; вариант WS+CDN |
| РФ-сервисы блокируют IP Hetzner | Режим A уже решает: РФ-трафик идёт напрямую |
| Белый список ломает сервис | Явные исключения по доменам; RUNBOOK с процедурой добавления |
| DPI научился ловить REALITY | Второй inbound (gRPC), UDP-канал, обновление Xray |
| Превышение 20 ТБ | vnstat + алерт; режим B резко снижает трафик |
| Abuse-жалоба Hetzner | Блок bittorrent на сервере, только личное использование |
| Ломающие изменения в Xray | Пин версии, тест на снапшоте перед апгрейдом |
| Компрометация панели | Случайный путь + 2FA + TLS + firewall/CF-allowlist, бэкап базы в Telegram |
| Блокировка домена панели | VPN от домена не зависит; запасной доступ к подписке по IP и через SSH-туннель |
