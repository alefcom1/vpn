# Прокси для веб-интерфейсов

Доступ к `chatgpt.com`, `claude.ai` и подобным из браузера, без VPN-клиента
и без системного тоннеля. Через сервер идут только указанные домены,
всё остальное — напрямую.

## Почему именно так

Обратный прокси для этих сайтов не делается: они за Cloudflare с антиботом,
вход через OAuth с привязкой `redirect_uri` к настоящему домену, куки привязаны
к домену, а JS-бандл ходит по захардкоженным адресам. Такая конструкция
ломается после каждого их релиза.

Прокси на уровне браузера этих проблем не имеет: запросы делает сам браузер,
со своими куками и своим TLS-отпечатком. Для Cloudflare это обычный посетитель,
просто с европейским адресом.

## Установка на сервере

```bash
sudo ./proxy/setup.sh
```

Поднимется один контейнер `webproxy` на порту 18443. Логин и пароль
сгенерируются сами и будут выведены в конце. Повторный запуск их не меняет.

Другой порт или имя пользователя:

```bash
sudo PROXY_PORT=22443 PROXY_USER=massimo ./proxy/setup.sh
```

Проверка с любой машины:

```bash
curl -x http://ЛОГИН:ПАРОЛЬ@178.105.192.76:18443 -s https://api.ipify.org
```

Должен вернуться адрес сервера. Вернулся домашний — трафик мимо прокси.

## Настройка браузера

Нужно расширение, умеющее правила по доменам: **Proxy SwitchyOmega**
(Chrome, Firefox) или **FoxyProxy**.

### SwitchyOmega

1. **New profile** → тип **Proxy** → имя, например `hetzner`.
2. Протокол **HTTP**, сервер — IP сервера, порт `18443`.
3. Кнопка с замком рядом со строкой — ввести логин и пароль.
4. **Auto Switch** → добавить правила:

| Условие | Профиль |
|---|---|
| `*.chatgpt.com` | hetzner |
| `*.openai.com` | hetzner |
| `*.oaistatic.com` | hetzner |
| `*.oaiusercontent.com` | hetzner |
| `*.claude.ai` | hetzner |
| `*.anthropic.com` | hetzner |
| всё остальное (default) | Direct |

5. Переключить режим расширения на **Auto Switch**.

Домены статики (`oaistatic`, `oaiusercontent`) добавлены не для красоты:
без них страница грузится, а картинки и файлы — нет.

### Важно про Chrome

Chrome **не поддерживает авторизацию в SOCKS5** — молча игнорирует логин
с паролем. Поэтому прокси именно HTTP: с ним Basic-авторизация работает
и в Chrome, и в Firefox.

## Проверка

1. Открыть `https://chatgpt.com` — должен открыться без ошибки региона.
2. Открыть любой российский сайт — должен работать напрямую, как обычно.
3. `docker logs webproxy --tail 20` на сервере — видны запросы.

## Безопасность

- Доступ только по паролю, `auth strong`: без него не пройдёт никто.
- Закрыты внутренние сети `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`.
  Без этого прокси стал бы дверью к соседним контейнерам и localhost —
  то есть к базам и админкам того, что крутится на сервере.
- Наружу разрешены только порты 80 и 443. Прокси нельзя использовать
  для рассылки почты или сканирования портов.
- Пароль не передавай дальше: по логам видно только, что ходили с сервера,
  но отвечать за чужие действия будет его владелец.

Расширить список портов (например, под какой-нибудь API на нестандартном порту)
можно в `proxy/3proxy.cfg.tmpl`, строка `allow`.

## Если начнут блокировать

Голый HTTP-прокси на нестандартном порту DPI видит как есть. Следующая ступень —
Caddy с плагином `forward_proxy` (схема NaiveProxy): прокси живёт на 443 под
обычным доменом и снаружи неотличим от сайта. Требует пересборки Caddy через
`xcaddy`, поэтому поднимать его стоит отдельным экземпляром, а не трогать боевой.

Начинать с этого не нужно — сперва проверить, что схема решает задачу.

## Удаление

```bash
cd /opt/webproxy && docker compose down
sudo rm -rf /opt/webproxy
docker rmi 3proxy/3proxy:latest
```

Больше ничего в системе не меняется: ни firewall, ни sysctl, ни SSH.
