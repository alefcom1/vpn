# Прокси для веб-интерфейсов

Доступ к `chatgpt.com`, `claude.ai` и подобным из браузера, без VPN-клиента
и без системного тоннеля. Через сервер идут только указанные домены,
всё остальное — напрямую.

## Почему именно так

Обратный прокси для этих сайтов не делается: они за Cloudflare с антиботом,
вход через OAuth с привязкой `redirect_uri` к настоящему домену, куки привязаны
к домену, а JS-бандл ходит по захардкоженным адресам. Такая конструкция
ломается после каждого их релиза.

Прокси на уровне браузера этих проблем не имеет: запросы делает сам браузер,
со своими куками и своим TLS-отпечатком. Для Cloudflare это обычный посетитель,
просто с европейским адресом.

## Установка на сервере

```bash
sudo ./proxy/setup.sh
```

Поднимется один контейнер `webproxy` на порту 18443. Логин и пароль
сгенерируются сами и будут выведены в конце. Повторный запуск их не меняет.

Другой порт или имя пользователя:

```bash
sudo PROXY_PORT=22443 PROXY_USER=massimo ./proxy/setup.sh
```

Проверка с любой машины:

```bash
curl -x http://ЛОГИН:ПАРОЛЬ@178.105.192.76:18443 -s https://api.ipify.org
```

Должен вернуться адрес сервера. Вернулся домашний — трафик мимо прокси.

## Настройка на устройстве

Расширение не нужно. Список доменов живёт в PAC-файле на сервере, устройство
забирает его само — и им одинаково пользуются Safari, Chrome и остальные
приложения, уважающие системные настройки прокси.

Для Safari это единственный рабочий путь: WebKit не позволяет расширениям
управлять прокси, поэтому FoxyProxy и аналоги там попросту не существуют.

Адрес PAC-файла печатает `setup.sh`, вид такой:

```
http://178.105.192.76:18444/<случайный токен>.pac
```

### macOS

Системные настройки → Сеть → Wi-Fi → **Подробности** → **Прокси** →
включить **Автоматическая настройка прокси** → вставить адрес PAC → Готово.

Делается **отдельно для каждого подключения**: Wi-Fi и Ethernet настраиваются
независимо, и настройка одного не действует на другое.

При первом обращении к прокси система спросит логин и пароль — поставить
галочку сохранения, дальше попадёт в Связку ключей и больше не спросит.

### iPhone и iPad

Настройки → Wi-Fi → (i) у своей сети → **HTTP-прокси** → **Автоматически** →
вставить адрес PAC.

Работает только по Wi-Fi: в мобильной сети настроек прокси нет. Для LTE
останется либо Happ, либо ничего.

### Windows

Параметры → Сеть и Интернет → Прокси → **Использовать сценарий настройки** →
вставить адрес.

### Если всё же хочется расширение в Chrome

Единственный живой вариант — **Proxy SwitchyOmega 3 (ZeroOmega)**: форк
оригинального SwitchyOmega под Manifest V3, он поддерживается. Сам
SwitchyOmega остался на MV2 и в Chrome уже не работает — отсюда и низкие
оценки у того, что выдаётся в поиске.

Смысл в нём один: быстро переключать режим кнопкой, не лазая в системные
настройки. Тип прокси — **HTTP** (Chrome молча игнорирует авторизацию
в SOCKS5), либо режим **PAC** с тем же адресом.

## Как менять список доменов

Список — `proxy/domains.txt`, один домен на строку, поддомены включаются
сами. После правки:

```bash
cd /root/vpn && git pull
sudo DIR=/opt/webproxy OUT=/opt/webproxy/pac/proxy.pac bash proxy/gen-pac.sh
```

Перезапускать ничего не надо: файл раздаётся статикой, устройства подтянут
его при следующем обновлении PAC (macOS перечитывает его при смене сети
или по таймеру; принудительно — выключить и включить галочку в настройках).

В конце файла есть закомментированный раздел с видеосервисами. Он выключен
намеренно: у сервера лимит 20 ТБ в месяц, и YouTube в 4K способен выбрать
сотни гигабайт одним человеком. Перед включением стоит посмотреть `vnstat -m`.

## Проверка

1. Открыть `https://chatgpt.com` — должен открыться без ошибки региона.
2. Открыть любой российский сайт — должен работать напрямую, как обычно.
3. `docker logs webproxy --tail 20` на сервере — видны запросы, и только
   к тем доменам, что есть в списке. Если там мелькает что-то постороннее —
   значит PAC не применился и трафик идёт через прокси целиком.

## Безопасность

- Доступ только по паролю, `auth strong`: без него не пройдёт никто.
- Закрыты внутренние сети `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`.
  Без этого прокси стал бы дверью к соседним контейнерам и localhost —
  то есть к базам и админкам того, что крутится на сервере.
- Наружу разрешены только порты 80 и 443. Прокси нельзя использовать
  для рассылки почты или сканирования портов.
- Пароль не передавай дальше: по логам видно только, что ходили с сервера,
  но отвечать за чужие действия будет его владелец.

Расширить список портов (например, под какой-нибудь API на нестандартном порту)
можно в `proxy/3proxy.cfg.tmpl`, строка `allow`.

## Если начнут блокировать

Голый HTTP-прокси на нестандартном порту DPI видит как есть. Следующая ступень —
Caddy с плагином `forward_proxy` (схема NaiveProxy): прокси живёт на 443 под
обычным доменом и снаружи неотличим от сайта. Требует пересборки Caddy через
`xcaddy`, поэтому поднимать его стоит отдельным экземпляром, а не трогать боевой.

Начинать с этого не нужно — сперва проверить, что схема решает задачу.

## Удаление

```bash
cd /opt/webproxy && docker compose down
sudo rm -rf /opt/webproxy
docker rmi 3proxy/3proxy:latest
```

И снять автоматическую настройку прокси в системных настройках устройств.

Больше ничего в системе не меняется: ни firewall, ни sysctl, ни SSH.
